# Orbit 제품 솔루션 제안

> 현재 구현된 기능을 기준으로, 핵심 사용 루프·데이터 신뢰성·컨텍스트 복구 관점에서 무엇을 먼저 해결할 것인가

작성일: 2026-08-06
전제 문서: [Orbit 제품 문제 정의](product-problem.md)

## 문서 목적

이 문서는 새 기능 목록이 아니다. 이미 구현된 기능(Task, Jira, GitHub, Calendar, Slack, Confluence, AI Chat, Dashboard)을 기준으로 `수집 → 집중·전환 → 재개 → 종료·학습` 루프의 어디가 끊겨 있는지 진단하고, 끊긴 지점을 잇는 최소 솔루션과 MVP 범위를 정한다.

---

## 1. 현재 구현 진단: 루프는 어디서 끊기는가

문제 정의 문서의 4단계 루프에 현재 구현을 대응시키면 다음과 같다.

| 루프 단계 | 구현된 것 | 끊긴 지점 |
|---|---|---|
| 수집 | Jira 티켓·PR·Slack 검색·AI 세션을 각 페이지에서 수동으로 Task에 연결. Task 생성 시 컨텍스트 자동 탐색(`TaskContextDiscoveryModal`). Chat의 `create_task` 제안 카드 | `inbox` 상태가 도메인에 있으나(`work-item.ts`) 아무것도 inbox로 유입되지 않는다. 새로 할당된 Jira 티켓, 저장한 Slack 요청이 사용자가 먼저 찾아가기 전에는 작업이 되지 않는다 |
| 집중·전환 | focus 단일 유지, focus 이탈·교체 시 체크포인트 강제 모달(`requiresCheckpoint` + `TransitionCheckpoint`) — **루프에서 가장 잘 구현된 부분** | `done`으로의 전환과 focus가 아닌 작업의 `blocked` 전환은 체크포인트 없이 통과한다. 막힌 이유·재개 조건을 담을 필드 자체가 없다 |
| 재개 | focus 패널 상단에 checkpoint·nextAction 표시. targetAt 초과 시 1회 알림 | **재개를 시작하는 화면이 없다.** 앱을 열었을 때 "어제 무엇을 하다 멈췄고 무엇부터 하면 되는지"를 보여주는 곳이 없다. Dashboard는 캐시 스냅숏 나열이고, 중단 시각·중단 사유는 기록되지 않아 오래 방치된 작업을 다시 떠올릴 트리거가 targetAt 하나뿐이다 |
| 종료·학습 | `completedAt` 기록 | **사실상 전무.** done 처리 시 Jira 상태는 그대로이고(Jira 연동은 읽기 전용), 무엇을 만들었고 무엇을 결정했는지 남지 않는다. 완료는 목록에서 사라지는 행위일 뿐이다 |

데이터 신뢰성 관점의 진단은 별도로 정리한다.

- **신선도가 보이지 않는다.** Jira 개발 정보만 30분 TTL(`JIRA_DEVELOPMENT_CACHE_TTL_MS`)이 있고, Jira 이슈·PR·Slack·Calendar는 페이지에서 수동 새로고침할 때만 갱신된다. Dashboard는 마운트 시 캐시를 1회 읽고 끝난다. 어느 화면에도 "마지막 동기화 시각"이 없어서, 어제의 캐시가 오늘의 현황처럼 보인다. 사이드바의 "로컬에 저장됨" 표시는 실제 동기화 상태와 무관한 고정 문구다.
- **상태 소유권 규칙이 없다.** AI 세션 완료 토글이 `taskStatusForSessions`를 거쳐 Task 상태를 직접 덮어쓴다(`App.tsx`의 `toggleSessionCompletion`). 사용자가 의도적으로 `review`로 옮겨둔 작업이 세션 토글 한 번에 `ai_running`이나 `done`으로 되돌아갈 수 있다. 자동화와 사용자 조작이 충돌할 때 누가 이기는지 정의되어 있지 않다.
- **Orbit 스스로 이중 장부를 만든다.** 문제 정의는 "실제 진행과 Jira 상태가 어긋나 티켓을 신뢰할 수 없다"고 지적하는데, 현재 Orbit은 Jira를 읽기만 하므로 Orbit에서 done 처리한 작업의 Jira 티켓은 여전히 In Progress다. 티켓 불신 문제를 해결하는 게 아니라 장부를 하나 더 늘린 상태다.
- **자동 연결의 근거가 약하다.** 컨텍스트 자동 연결은 토큰 겹침 점수(`contextMatchScore`) 기반이라 한국어 제목에서 정밀도가 떨어질 수 있다. 점수·사유(reason) 필드는 있으므로, 문제는 알고리즘보다 "왜 연결됐는지, 틀렸으면 어떻게 해제하는지"를 사용자에게 돌려주는 표면이 얇다는 점이다.

컨텍스트 복구 관점에서는, 문제 정의 문서가 요구한 "재개 가능한 작업 상태" 8요소 중 구현된 것은 목적(goal)·체크포인트·다음 행동·완료 조건(doneDefinition, 단 생성 폼에는 입력란이 없음) 4개다. 막힌 이유와 재개 조건, 중단 시점, 진행 중 결정 기록, 관련 링크의 스냅숏은 스키마에도 없다.

## 2. 설계 원칙

솔루션을 고르는 기준을 먼저 정한다.

1. **루프를 완성하는 것이 기능을 늘리는 것보다 먼저다.** 수집·집중은 이미 절반 이상 있다. 가장 크게 비어 있는 재개와 종료를 잇는다.
2. **이미 가진 데이터로 초안을 만든다.** 연결된 AI 세션의 마지막 요청, Jira 개발 정보의 커밋·PR은 이미 로컬 DB에 있다. 사용자에게 빈 텍스트박스를 주지 말고 이 데이터로 미리 채운 초안을 준다.
3. **자동화는 실행이 아니라 제안이다.** 상태를 바꾸는 자동화(세션→Task 전이, 자동 연결)는 사용자가 승인하는 제안으로 강등한다. Chat의 `create_task` 승인 카드가 이미 이 패턴을 쓰고 있으므로 제품 전반의 규칙으로 승격한다.
4. **신선도는 데이터의 속성으로 취급한다.** 언제 동기화됐는지 모르는 데이터는 보여주지 않는 것보다 나쁘다.

## 3. 솔루션

### 3.1 재개 브리핑 — Dashboard를 "오늘의 시작 지점"으로 재정의

**문제**: 재개 단계가 통째로 비어 있다. 컨텍스트 복구는 정보가 저장돼 있어도 다시 보여주는 순간이 없으면 일어나지 않는다.

**솔루션**: Dashboard 최상단을 정적 목록에서 재개 브리핑으로 바꾼다.

- **1순위 카드 — 이어서 시작**: 마지막 focus였던 작업(또는 최근 체크포인트가 있는 작업)을 "어제 {checkpoint}까지 했고, 다음은 {nextAction}"의 한 문장으로 보여주고, 버튼 하나로 focus 전환까지 처리한다. 필요한 데이터(checkpoint, nextAction, updatedAt)는 전부 있다. 부족한 것은 "마지막 focus가 누구였는지"의 기록뿐이다.
- **2순위 — 막힌 작업 재점검**: `blocked` 작업마다 저장된 재개 조건(3.2에서 추가)을 보여주고 "조건이 풀렸나요?"를 묻는다. 풀렸으면 todo/focus로, 아니면 다음 확인 시점을 미룬다.
- **3순위 — 방치 감지**: `review`·`ai_running` 상태로 N일 이상 갱신이 없는 작업을 "잊힌 작업"으로 올린다. 문제 정의의 "B 작업의 존재 자체를 놓친다"에 대한 직접 응답이다.

기존 오늘 일정·PR 패널은 브리핑 아래로 내린다. 삭제가 아니라 우선순위 재배치다.

### 3.2 체크포인트의 구조화 — blocked에 이유와 재개 조건을 필수화

**문제**: 체크포인트가 자유 텍스트 2필드(현재까지 한 것/다음 행동)뿐이고, 정작 가장 복구가 어려운 `blocked` 전환에는 아무것도 묻지 않는다.

**솔루션**:

- **blocked 전환 모달**: focus 전환에 이미 쓰는 `TransitionCheckpoint` 패턴을 재사용해, blocked 전환 시 "왜 막혔나(사유)"와 "무엇이 되면 재개하나(재개 조건)" 2필드를 필수로 받는다. 스키마에 `blockedReason`, `resumeCondition`, `pausedAt` 3필드를 추가한다.
- **체크포인트 자동 초안**: 전환 모달을 열 때 연결된 AI 세션의 마지막 요청(`lastPrompt`), Jira 개발 정보의 최근 커밋 메시지를 초안으로 미리 채운다. "빈 칸 채우기"를 "확인하고 고치기"로 바꿔 전환 마찰을 낮춘다. 강제 입력의 가장 큰 리스크는 사용자가 귀찮아서 아무 말이나 적는 것인데, 초안이 그 비용을 흡수한다.
- **중단 시각 자동 기록**: focus에서 이탈하는 모든 전환에 `pausedAt`을 자동 기록해 재개 브리핑과 방치 감지의 기준으로 쓴다.

### 3.3 완료 시트 — 출구 루프 만들기

**문제**: done은 현재 "목록에서 치우기"다. 문제 정의가 요구한 종료·학습(외부 도구 동기화 + 결과·결정 기록)이 없다.

**솔루션**: done 전환 시 완료 시트를 띄운다. 세 블록으로 구성한다.

1. **결과 요약(자동 초안)**: 연결된 PR(머지 여부)·커밋 수·세션 목록으로 "무엇을 만들었는지"를 자동 생성하고 사용자가 다듬는다.
2. **Jira 동기화(선택 실행)**: 연결된 Jira 티켓이 있으면 "티켓도 Done으로 전이" 체크박스를 보여준다. 이것이 Jira 연동에 필요한 **유일한 쓰기 API**(transition 1개)이며, "실제 작업과 티켓 관리의 분리" 문제에 대한 최소 응답이다. 실패하면 Task 완료는 유지하고 티켓 전이만 재시도 큐에 남긴다 — 사용자의 완료 선언이 외부 API 실패에 볼모로 잡히면 안 된다.
3. **회고 한 줄(선택)**: "다음엔 무엇을 다르게 할까" 1필드. 학습 기록은 부담이 없어야 쌓인다.

완료 기록은 삭제하지 않고 작업 로그로 보존해, 이후 "어제 한 작업" 패널과 주간 회고의 원료가 되게 한다.

### 3.4 데이터 신뢰성 — 신선도 표면화와 상태 소유권 규칙

**문제**: 캐시가 언제 것인지 보이지 않고, 자동 전이가 사용자 조작을 덮어쓴다.

**솔루션**:

- **소스별 `lastSyncedAt` 노출**: Jira·PR·Slack·Calendar 캐시 테이블에 이미 있는 `discovered_at`/`synced_at` 계열 값을 각 페이지 헤더와 Dashboard 패널에 "12분 전 동기화"로 표시한다. TTL 초과 시 흐림 처리 + 새로고침 버튼. 구현 비용 대비 신뢰 회복 효과가 가장 큰 항목이다.
- **동기화 정책 통일**: 소스마다 제각각인 갱신 시점을 "앱 포그라운드 진입 시 + 소스별 TTL 경과 시"라는 하나의 규칙으로 통일한다. Jira 개발 정보의 30분 TTL 패턴을 다른 소스로 확장하는 것이므로 새 개념이 아니다.
- **상태 소유권 규칙 — 사용자가 항상 이긴다**: 세션 완료 토글에 의한 Task 상태 변경을 즉시 실행에서 제안으로 바꾼다. 모든 세션이 완료되면 Task를 `done`으로 바꾸는 대신 `review`에 두고 "AI 작업이 끝났습니다. 확인 후 완료하세요"를 표시한다. `review`(내 확인 필요) 상태가 정확히 이 용도로 이미 존재한다.
- **자동 연결의 근거 노출**: 자동 연결된 컨텍스트에는 연결 사유(이미 있는 `reason` 필드)와 "자동 연결됨" 배지를 붙이고 원클릭 해제를 유지한다. 정밀도 개선(임베딩 등)은 오연결이 실측으로 문제가 될 때로 미룬다.

### 3.5 수집 — inbox를 제안 큐로 살리기

**문제**: 수집이 전부 풀(pull)이다. 사용자가 Jira 페이지·Slack 검색에 먼저 가야 작업이 생긴다.

**솔루션**: 동기화 시 발견되는 "내게 새로 할당된 Jira 티켓"과 사용자가 Slack 페이지에서 저장한 메시지를 **inbox 제안**으로 쌓는다. 자동으로 Task를 만들지 않고(원칙 3), inbox 탭과 재개 브리핑 하단에서 "Task로 승격 / 무시"를 고르게 한다. Chat 승인 카드와 동일한 승인 UX를 쓴다. 단, 이 항목은 3.1~3.4보다 후순위다 — 수집은 이미 절반 있고, 재개·종료는 0이기 때문이다.

## 4. MVP 범위

세 릴리스로 자른다. 각 릴리스는 독립적으로 가치가 있고, 순서는 "루프의 빈 곳이 큰 순 + 구현 비용이 낮은 순"이다.

### MVP 1 — 컨텍스트 복구 (재개 루프 완성)

- 재개 브리핑 카드(이어서 시작 + 방치 감지)로 Dashboard 최상단 교체
- `blockedReason` / `resumeCondition` / `pausedAt` 필드 추가, blocked 전환 모달 필수화
- 전환 모달 체크포인트 자동 초안(세션 lastPrompt·최근 커밋 기반)

**제외**: 회고·주간 리포트, 임베딩 기반 연결, 알림 고도화.
**성공 지표**: 앱 시작 → 첫 상태 전이까지 시간 단축, 체크포인트 보유 작업 비율, 7일 이상 무갱신 작업 수 감소.

### MVP 2 — 데이터 신뢰성

- 전 소스 `lastSyncedAt` 표시 + stale 처리 + 수동 새로고침 통일
- 포그라운드 진입 + TTL 기반 동기화 스케줄러
- 세션 완료 자동 전이를 `review` 제안으로 강등

**제외**: 실시간 웹훅, 백그라운드 데몬 동기화.
**성공 지표**: Dashboard 데이터 평균 나이, 자동 전이를 사용자가 되돌리는 빈도(제안 거절률로 측정 가능해짐).

### MVP 3 — 출구 루프

- 완료 시트(결과 요약 자동 초안 + 회고 한 줄)
- Jira 상태 전이 write-back 1종 + 실패 재시도 큐
- 완료 로그 보존 및 "어제 한 작업" 패널 연결

**제외**: Slack 완료 공지 자동화, Confluence 문서화 자동화, AI 회고 생성.
**성공 지표**: Orbit done ↔ Jira Done 불일치 건수, 완료 시트 작성률.

## 5. 판단 근거 요약

문제 정의 문서의 제품 판단 기준 5문항에 대응시키면:

| 판단 기준 | 대응 솔루션 |
|---|---|
| 1. 작업 유실 감소 | 3.1 방치 감지, 3.5 inbox 제안 |
| 2. 중단 시 맥락·다음 행동 보존 | 3.2 구조화 체크포인트 |
